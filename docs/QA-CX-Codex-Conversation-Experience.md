## CX-CE-01 排队消息A改为B，取消确认丢失且A先开始

- 目标：内容修改不会复用旧请求身份，也不会篡改已经执行的历史。
- 角色：编辑排队消息的手机用户；安排确认丢失与事件顺序的验收人员。
- 前提：当前轮次运行；A已获服务端入队确认，具有已记录的displayMessageId和clientMessageId；B与A正文不同。
- 操作与逐步可观察结果：
  1. 编辑A为B并提交修改，同时丢弃取消A的ACK → 界面显示正在确认取消；保留A原始内容与B待修改内容，尚未发送B，不显示取消成功。
  2. 在确认期间使旧A先开始，并送达其权威开始事件 → A对应历史保持原文；B回到草稿，不自动另发B。
  3. 恢复取消查询、通知和快照 → 收敛到A已经开始的事实；执行证据只有A，不出现由此次编辑自动启动的B。
  4. 使用独立初始样本重做编辑，让服务端明确确认A已取消且不会开始 → 此时才可改发B；B取得新的clientMessageId并保持displayMessageId，不能使用A的请求ID承载新内容。
  5. 对照两条分支的气泡与身份记录 → outbox、队列及服务端确认的展示转换保持稳定displayMessageId；它与clientMessageId承担不同职责，不能用稳定UI身份要求复用旧请求ID。
- 失败门槛：取消结果未知时发送B、A开始后自动发送B、A历史被改为B、内容变化仍沿用A的clientMessageId，任一项即失败。

## CX-CE-02 同内容确认丢失重试，404之后晚到turn

- 候选进度：普通发送已传原生`clientUserMessageId`，snapshot/live读取`clientId`。早期202不含turn/opener、原生快照先到时，393/1365隔离浏览器已保持1用户/1轮次、原节点/选区/滚动，并在snapshot清outbox；无身份对照仍保守保留2条，不冒认完整兼容通过。新版turn/start可以接续活动轮，因此上一候选opener推断已撤回。相同原生身份的live UUID与snapshot item-1一对一关联和缓存保留已有专项证据；真实CLI加回环假模型验证重启保持clientId，但不是完整真实服务一次执行验收。日志回退、新任务预览交接、同轮后续用户消息及完整网络矩阵仍待验证。以下完整验收标准不变。
- 日志回退补充：直接保留事件自身的client_id，已覆盖全量/增量、UTF-8/CRLF、半行补齐、生命周期冲突、同文独立client、路径替换及图片。双源opener替换已按规范UI来源修正；现对文件头可信且显式legacy的raw-first再从读取入口选择UI历史，原文件不改。完整头指纹保护模式判断，已知空历史不触发heavy RPC，隔离证据见`tests.md`。**完整场景仍未放行**：未知格式raw-only、paginated日志、新任务交接、任务状态与真实执行次数须独立验收。
- 显示回归步骤：保留含`internal_chat_message_metadata_passthrough.turn_id`及`content_item_kinds`的原生双源JSONL；从本地气泡→202→真实reader快照→公开刷新，逐阶段检查同一物理user/turn节点、display/render key、DOM Range、滚动及outbox。再用同turn不同client的相同正文验证两条气泡都可见，不能只检查投影数量；只有B的证据不得确认A。重载只断言逻辑身份和不重发，不要求跨document节点相同。
- raw-first回归：首个完整非空meta必须ID匹配并显式legacy；202之后先仅写模型输入并用真实reader刷新，再追加同轮UI事件并刷新。中间态也必须1气泡且保留原节点/选区/滚动；只到raw不得确认outbox，事件自身身份到达才确认。分别验证头在24MB尾窗外、512字节外等长改mode后追加、文件替换及后续fork metadata不覆盖首头。未知或缺失头作为保守兼容控制，不能按正文误确认；不将其两条气泡记为通过零重复。
- 目标：同一逻辑发送只产生一条用户消息和一次实际执行，未知送达不误报失败。
- 角色：发送并尝试重试的用户；注入响应与事件延迟的验收人员。
- 前提：服务端已接受正文A；丢弃ACK，恢复查询先返回404；原请求clientMessageId已记录。
- 操作与逐步可观察结果：
  1. 发送A并等待请求超时 → 原气泡保持可见，提示正在确认送达；不显示红色“未发送”或发送失败。
  2. 触发同内容网络重放，再收到404 → 继续核对原逻辑请求；网络重放复用原clientMessageId，不另建请求身份或盲目启动新turn。只有确认旧执行尝试不会开始后，用户显式重试才可用新clientMessageId并保持displayMessageId。
  3. 在404后送达原请求的接受、turn开始及完成事件 → 原位确认送达并展示对应结果，气泡不删除重插、不多出第二条。
  4. 重放上述事件并检查服务端执行记录 → 同一请求只关联一次实际执行；重复通知不再触发执行或错误提示。
  5. 使用独立样本让所有核对证据持续缺失直到恢复预算耗尽 → 显示暂时无法确认送达及重新检查/复制入口，不无限恢复、不自动重发可能已执行的请求。
- 失败门槛：ACK丢失、超时或404单独触发红色失败；同内容网络重放换新请求ID；重复气泡、双执行或无预算恢复，任一项即失败。

## CX-CE-03 执行、目标与连接的组合状态

- 目标：主状态由权威执行事实决定，连接和目标信息不抹掉完成结果或待处理审批。
- 角色：查看状态、处理审批的用户；构造组合事实的验收人员。
- 前提：分别准备已完成轮次、持续目标下的运行轮次、等待审批轮次；每个样本均可控制连接状态。
- 操作与逐步可观察结果：
  1. 先确认轮次完成，再断网 → 最终结果和完成事实保留，运行动画停止；断网作为附加信息显示，不能把完成改成正在处理或正在恢复执行。
  2. 在当前轮次仍running时暂停持续目标 → 主状态仍表示当前轮次正在处理；目标暂停说明停止后续自动续跑，不提前声称当前轮次已暂停或结束。
  3. 在等待审批时断网 → 审批问题保持首层可见，主状态显示“需要确认（上次状态）”并说明连接情况；问题仅可查看，不能用断网提示覆盖审批，也不能继续显示思考动画或累计处理用时。
  4. 断网时尝试审批，再恢复连接 → 断网期间提交入口不可用；重新核对审批仍有效后才允许用户提交，不能伪装已提交或已批准；只有权威接收/执行事实才能推进状态，恢复过程不自动批准、不重复创建审批卡片。
  5. 逐一检查所有组合 → 当前会话只有一个主要状态栏，历史轮次不重复显示活动动画；耗时、动画和操作能力不互相矛盾。
- 失败门槛：完成被断网覆盖、目标暂停把当前running误判成停止、审批被隐藏/自动批准，或重复主状态栏，任一项即失败。

## CX-CE-04 公开commentary原样显示，结构化工具详情默认隐藏

- 目标：按事件来源分层，保留模型面向用户的文字和代码。
- 角色：默认阅读进展并按需检查操作详情的用户。
- 前提：准备含`npm test`的commentary、含多行代码块的commentary，以及独立结构化命令、stdout、原始JSON和diff事件。
- 操作与逐步可观察结果：
  1. 依次送达两段commentary → 文字、`npm test`和代码块不因关键词或代码格式被删除，身份及顺序不变；流式代码保持展开，已完成且超过12行的代码块可按PRD折叠，但须能展开和完整复制，选区或焦点位于其中时不得自动折叠。
  2. 送达结构化工具命令与stdout等事件 → 默认正文不新增这些详情；已有commentary不被工具标签、命令或日志替换。
  3. 打开查看操作详情 → 可以按真实turn/item身份查看命令和输出；没有显式关联ID时仅按阶段/本轮归组，不编造因果关系。
  4. 关闭详情并继续接收工具事件 → 公开文字仍在；手机默认不挂载完整命令输出或diff。
- 失败门槛：删改commentary中的命令/代码、工具输出默认泄入正文、工具事件顶掉文字或猜造关联，任一项即失败。

## CX-CE-05 手机键盘打开时保持阅读锚点、选区与唯一状态栏

- 目标：新进展不会破坏用户正在阅读或选择的内容。
- 角色：使用真实手机阅读长进展、选中文本并编辑草稿的用户。
- 前提：393×852视口，软件键盘打开，Composer有未提交草稿；前两段commentary均超过一屏，当前轮次仍运行。
- 操作与逐步可观察结果：
  1. 保持键盘打开并上滑阅读第一段 → 页面保留阅读位置；主状态栏固定在Composer上缘，在键盘上方可见且只有一个，不依赖正文滚到底部。
  2. 在正读段落选中文字，记录选区、焦点和阅读锚点 → 文本可选择，草稿保持；若系统选区操作收起键盘，另保留键盘打开的独立分支记录。
  3. 送达第三段commentary → 不因“最近两段”规则移除正读内容或选区，不替换其DOM导致选择失效，不自动滚到底部、不抢焦点、不清空草稿。
  4. 展开此前进展后继续接收文本及最终结果 → 展开状态与阅读锚点保留，结果不强制收起正读内容；状态栏仍不遮挡正文末行或Composer。
  5. 用户主动回到最新 → 才恢复跟随输出；仅在不会破坏阅读/选区时收敛默认可见段落，较早文字仍能打开。
- 失败门槛：第三段到达导致正读段消失、选区丢失、视口跳转、焦点被抢，或状态栏重复/被键盘遮挡/偏离Composer上缘，任一项即失败。

## CX-CE-06 部分final后失败或中断，随后重放旧running

- 目标：可读回答与执行终态分别可信，旧事件不能复活已结束轮次。
- 角色：阅读流式结果及恢复提示的用户；安排事件重放的验收人员。
- 前提：同一轮次已开始，部分显式final已到达，权威终态尚未到达；分别准备失败与中断两个分支。
- 操作与逐步可观察结果：
  1. 送达部分final并延迟剩余工具输出 → final立即可读；当前仍running时主状态不因已有文本而提前宣布完成。
  2. 分别送达权威失败/中断终态 → 保留部分final，首层独立显示本次未完成/已中断及适用恢复入口；动画停止，用时按权威终态冻结。
  3. 重放旧running、晚到工具输出和旧快照 → 终态不回退，不重启动画或计时，部分final不被挤走或误标为完整成功结果。
  4. 对照原用户气泡 → 已确认送达状态保持；执行失败不能改成发送失败。
- 失败门槛：部分final被删除、错误仅藏在详情、出现错误成功结论、旧running复活任务或已送达气泡变发送失败，任一项即失败。

## CX-CE-07 性能计时覆盖浏览器接收事件到内容实际可见

- 目标：前端呈现延迟与网络/服务等待分开，性能统计可复核。
- 角色：采集浏览器帧、接收时间和可见性证据的验收人员。
- 前提：记录设备、网络、版本与计时来源；分别准备首次/已有会话、排队、恢复样本及后台/滚出视口样本。
- 操作与逐步可观察结果：
  1. 浏览器收到权威开始事件或公开文本时记录`t_receive` → 分别对应PRD的`tStartReceived`和`tTextReceived`，文本起点不得晚于Markdown处理；服务端发送、Bridge排队及网络耗时另列，不混入前端呈现指标，也不直接相减未经校准的两端时钟。
  2. 对应状态栏/文本完成DOM更新并在当前视口实际可读时记录`t_visible` → 用帧记录及截图/录像核对；入队、状态赋值、节点创建或单次动画帧回调不能单独证明可见。
  3. 计算`t_visible - t_receive`并按场景分别报告 → 前台运行状态、公开文本呈现各自P95≤100ms；有效提交至气泡实际可见单独计时，P95≤100ms，附件上传另计。
  4. 收到内容时页面在后台、目标节点未挂载或不在可见视口 → 样本标记具体不可见原因，保留样本数与状态；不得将缺失终点填0，也不得悄悄删除样本美化P95。
  5. 汇总首次/已有会话各至少30个正常样本及异常每类至少10个样本 → 分列有效可见、不可见、未取得终点和失败数量；本机、桌面模拟、公网真机结果分开报告。
- 失败门槛：用服务器时间或DOM挂载替代可见端点、将网络延迟混算、不可见样本记0、隐藏缺失样本，或任一规定可见样本组P95超门槛，即失败；样本不足记未验证。

## CX-CE-08 手机后台两分钟后自动恢复，无需手动刷新

- 目标：后台返回自动保留内容并收敛真实状态；本场景仅定义，当前不执行两分钟等待或真机操作。
- 角色：把应用切后台再返回的真实手机用户。
- 前提：分别准备后台期间完成、持续running、等待审批、连接中断四种样本；保存进入后台前的文字、草稿、阅读位置和权威时间锚点。
- 操作与逐步可观察结果：
  1. 每个样本切后台两分钟后返回 → 原内容与草稿先保留，系统自动核对状态；用户不需要手动刷新、重新打开任务或重发消息。
  2. 后台已完成样本恢复 → 自动呈现完成结果并停止运行效果，不保留无限思考；终态不被旧running重放覆盖。
  3. 后台仍running样本恢复 → 根据新事实显示运行状态，用时接续权威锚点，不从00:00重新计时、不靠后台timer次数累计。
  4. 后台等待审批样本恢复 → 审批保持首层可见且不重复，等待用时与处理用时区分，不自动批准。
  5. 断网样本返回并随后恢复网络 → 内容保持，连接提示真实；恢复后自动补齐并核对送达/执行，遵守恢复预算，不重复执行、不抢阅读焦点。
- 失败门槛：必须手动刷新才能收敛、内容/草稿丢失、用时归零、重复执行/审批、后台完成仍无限运行，任一项即失败；只有桌面尺寸模拟证据时仍记真机未验证。
