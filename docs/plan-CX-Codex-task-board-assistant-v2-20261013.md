# CX-Codex：任务看板 + 助手窗口 规划 v2

日期：2026-10-13。状态：**规划草案，待评审**。本文作废同目录 `plan-CX-Codex-assistant-board-20261013.md` 中「执行侧 = Hermes」的框架（那是错误方向），并取代它的分期建议。仍然有效并可沿用的内容：未知态不等于失败、accepted 不等于 finished、分歧显式化、最小写入面、复用既有 Runtime 不造第二状态机。

## 0. 定位（先纠正方向）

CX-Codex 的定位是**远程 Codex 工具的精简高效版**，不是 Codex 桌面端的复刻。差异点只有两个：

1. **任务看板**：以「任务」为单位看进展；点开一张卡，能看到该任务对应的 Codex 会话线程与完整聊天记录。
2. **助手窗口**：直接在窗口里跟助手说话，助手自己把话变成任务、派发到 Codex 线程去跑；全过程可控、可视。

Hermes 与本产品无任何关系——它只是这个项目的施工方。上一版规划里把"执行侧"写成 Hermes 是我的误读，本版全部删除。

## 1. 概念模型（新增一层薄封装）

现状：CX-Codex 的一等公民是**线程**，已有 `/runtime/send`、`/runtime/queue(+reorder)`、`/runtime/interrupt`、`/runtime/snapshots`、`/runtime/events`，前端已有 transcript 渲染与移动端推送。

新增一层**任务（task）**，它只是「意图 + 关联线程 + 协作状态」的壳：

| 字段 | 说明 |
| --- | --- |
| taskId | 任务主键 |
| title / goal | 标题与目标（助手或用户填写） |
| source | 用户直说 / 助手派发 |
| threadIds | 关联的 Codex 线程（通常 1 个；一个主线程 + 子线程时按数组） |
| column | 看板列：待处理 / 进行中 / 阻塞 / 关闭 |
| needsConfirm | 是否需要用户确认后才真正派发 |
| blockedReason / closedReason | 阻塞原因（等待输入、等待权限、失败）/ 关闭原因 |
| createdAt / updatedAt / lastEventAt | 时间 |
| workspace | 工作目录（派发给线程时使用） |

**硬约束**：任务不复制线程运行态。线程到底在不在跑、队列里有什么、是否等待权限，一律实时取现有 runtime 快照与队列；任务只存"我要它做什么"和"协作到哪一步"。这样不存在第二状态机，也不会出现两套状态打架。

## 2. 助手（Assistant）

助手是 CX-Codex 内的一个**常驻会话线程**（复用现有线程机制，固定其 threadId 存为 assistant thread），带一组受控工具：

| 工具 | 作用 | 落地 |
| --- | --- | --- |
| `list_tasks` | 看待办与在跑的任务 | 读 task 表 |
| `create_task` | 建任务并创建对应 Codex 线程 | 建 task + 新建线程 |
| `dispatch` | 把指令发给某任务的线程 | 走现有 `/runtime/send` |
| `read_task` | 读该任务的线程记录与运行态 | transcript + snapshots |
| `stop_task` | 停止 | 走现有 `/runtime/interrupt` |
| `ask_user` | 需要用户决定时提问 | 任务进入"阻塞"，卡片与聊天里可见可答 |

**可控的三道闸门**：
1. 派发前确认：默认 `needsConfirm=true`，用户在卡片上点确认才真正 send；可对某任务或全局改成自动。
2. 工具白名单：助手默认只拿到上面 6 个协调工具，不开放 shell、不开放文件写入；任务明确需要时按任务授权，授权记录进任务时间线。
3. 随时可停：卡片和聊天里都能停；停止走 interrupt，且**未收到回执证实前显示"停止中"**，不显示已停止。

**可视**：助手每次工具调用都产生一条任务事件（谁触发、何时、参数摘要、结果），卡片时间线可见；点开卡片直接看线程里真实跑的内容，不需要用户去别处找。

## 3. 看板设计

四列：**待处理**（已建、未派发，含待确认）/ **进行中**（已派发，线程在跑或有队列）/ **阻塞**（等输入、等权限、失败）/ **关闭**（完成或人工关闭）。

卡片显示：标题、列、关联线程、最后活动时间、等待秒数、状态徽标（含"未知/陈旧"黄条）、阻塞原因。点开卡片 → 详情面板：该任务的会话线程与完整聊天记录（复用现有 transcript）、事件时间线（创建/确认/派发/停止/完成）、操作按钮（确认派发、停止、重开、关闭）。

列怎么算：**任务列由任务字段 + 线程实时态共同派生**；两者冲突时以任务字段为准并在卡上标注"运行态与列不一致"，绝不自动改用户的列。

拖拽（第二期起）：因为任务与列是本产品自己的对象，拖拽**直接改列是合理且可靠的**——这一点与上一版不同：上一版把列当成跨系统协议状态，所以只能写"意图"。现在：
- 拖到"进行中" = 触发派发（`needsConfirm=true` 时先弹确认；跑着的不重复派发）。
- 拖到"关闭" = 关闭任务；若线程仍在跑，先发 interrupt 并等回执证实，未证实显示"关闭中-待确认"。
- 拖到"阻塞" = 标记人工阻塞 + 必须填原因。
- 从"关闭"拖回 = 重开，保留全部历史消息，不覆盖。
- 非法拖动（例如把正在跑的任务直接拖成"已完成"而无中断、把无线程的任务拖到"进行中"）→ 弹回并给出明确原因。

## 4. 后端与数据

- 新增 `task` 与 `task_events` 两张表（本产品业务状态，放在现有 runtime 库同目录的独立库里，避免与 runtime 事务耦合）。
- 新增接口：`GET /codex-api/tasks`（列表，带列与线程运行时态）、`POST /codex-api/tasks`、`GET /codex-api/tasks/:id`（详情 + 线程 transcript）、`PATCH /codex-api/tasks/:id`（改列 / 关闭 / 重开 / 确认派发）。派发与停止仍复用 `/runtime/send` 与 `/runtime/interrupt`，不新增发送通路。
- 助手会话：作为固定线程存在；其工具调用通过现有事件通道记录，前端复用现有事件订阅与 transcript。
- 移动端：复用现有 `mobile-push`，任务进入"阻塞"或需要确认时推送。

## 5. 分期与验收

| 期 | 内容 | 验收 |
| --- | --- | --- |
| P1（约 1 周）骨架 | task 表 + 最小 API + 只读看板页（四列、卡片、点开看线程记录） | 卡片信息与线程 transcript 一致；列派生规则明确；刷新/断线不丢状态；**不做自动派发** |
| P2（约 1–2 周）助手 | 助手会话 + 6 个工具 + 确认闸门；聊天窗口与看板联动 | 创建/派发/读取/停止各跑通一次真实端到端；每次动作在任务时间线可见；未确认不派发；停止未证实显示"停止中" |
| P3（约 1 周）易用性 | 拖拽列迁移、阻塞与通知、任务模板、复用现有队列重排 | 拖拽矩阵逐格验证；"关闭"前先中断并证实；重开不覆盖历史 |

## 6. 与既有 PRD/P0 的关系

`PRD-CX-Codex-Personal-Assistant-Lite-v0.5` 与 `CX-Codex-Assistant-P0-Protocol-Review` 定义的是同一个助手的**协议层**（可信来源绑定、单槽、外发门闩、冷恢复、两类记录）。本规划是它的**产品层**：看板与聊天窗口是脸，协议层是脏器。两者不冲突，建议：

- 协议层继续按 D1→D4 推进（尤其"派发只接受可信用户来源、单槽、每段首次发送权"这三条，是助手不会乱跑的根基）。
- 产品层可与协议层并行：P1 不触发派发，P2 的派发接入 D1 完成后即天然合规。
- 助手"自动跑任务"的范围一开始就限定在**本产品自己的线程**（本机/已配置工作区），不做跨机器调度。

## 7. 明确不做

Hermes 集成（本轮明确排除）、跨系统对账、Codex 桌面端全量功能复刻、多用户/多租户、跨机器调度、让助手直接改权威运行态（一律经现有 send/interrupt 通路）、第一期做拖拽。
