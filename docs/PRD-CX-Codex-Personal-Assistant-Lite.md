# CX-Codex 核心私人助手：轻量第一版

日期：2026-10-13  
方案版本：0.4（轻量推荐方案）  
状态：历史 v0.4 草案；当前开发方案见 [v0.5](PRD-CX-Codex-Personal-Assistant-Lite-v0.5.md)，已结合正式版源码与 Hermes 学习复核调整。产品功能尚未实现。

本方案取代 v0.3 的第一版范围；[完整设计](PRD-CX-Codex-Personal-Assistant.md)保留为后续参考。用户要求先不写代码，本轮仅调整文档。`PRODUCT_GOAL.md` 的优先级和必需门槛保持有效。

## 1. 摘要

一个固定私人助手接收需求，简单问题直接回答，执行任务交给一个后台 Codex 工作线程，结束后由助手转述结果。第一版只管理一次受理、一次执行、一次自动回传；沿用现有 Runtime、SQLite、队列、审批和会话投影。

关键取舍：取消同任务续办/修订和事务式业务验收发布。一次受理后的执行契约不再修改；补充执行创建关联的新任务。助手说明检查和未验证项，任务卡只显示真实执行状态。

## 2. 参与者

| 参与者 | 职责 |
| --- | --- |
| 用户 | 提出目标、澄清歧义、决定授权、查看结果 |
| 主助手 | 简单问答，调用派发/查询/停止工具，解释后台结果 |
| 工作线程 | 在冻结的项目和权限范围内执行，产生普通原生 final |
| 服务端协调模块 | 保存任务关系，串行调度，捕获结果，回传和重启对账 |

## 3. 简化依据

v0.3 的执行链、问题生命周期、批次领取和发布事务，是为“原任务持续更正”和“系统核验后正式结算业务成功”服务的。第一版收缩这两项承诺，可以直接删掉相应机制；派发去重和重启安全仍需程序保证。

现有源码已提供 SQLite/WAL、稳定 clientMessageId、Runtime 请求记录、队列和原生审批。仍需新增动态工具处理、可信消息来源/实际 turn 关联，以及 RPC 发出前的持久门闩；这些缺口不能用提示词或已有队列代替。事实与固定提交调研见 v0.3 第 3 节及[GitHub 调研](research-CX-Codex-personal-assistant-github-20261013.md)。

## 4. 第一版目标

- 用户只面对一个助手入口；后台线程可按需查看。
- 简单问答不创建工作线程；派发持久受理后立即返回，助手可以继续交流。
- 托管后台执行最多一个；任务状态未知、等待输入或停止未证实时仍占用槽位。
- 同一派发重投不重复启动；结果落盘后才回传，关闭网页不会丢失任务关系。
- 重启核对原执行和原回传；不因超时或服务重启重新执行未知任务。
- 不自动把模型说的“成功”变成业务验收结论；原审批与工作区边界继续有效。

## 6. 用户体验与明确边界

用户说“分析项目 A 的发送流程”时，助手派发并返回任务编号；用户可以接着问其他问题。工作线程结束后，助手说明结果、出处、检查和剩余问题，任务详情可打开原始执行记录。

项目或目标不明时在正常聊天中澄清，不为每次派发增加确认点击。一条用户请求第一版最多受理一个独立执行任务；关联步骤放在同一目标中，多个独立目标先确定本次处理范围。

用户说“继续刚才的分析”时，创建关联的新任务。用户要求改变正在执行的目标时，先停止原执行并核对终态，再以新要求派发；停止不确定时不能启动替代执行。原任务契约和已回传正文不被改写。

任务卡使用“排队、执行中、等待处理、停止中、执行结束、执行失败、状态待核对”等表述，状态来自绑定的 Runtime/原生事实。“执行结束”不等于目标达成；助手的自然语言结论不修改任务状态。缺少 final 或检查证据时说明未验证，不推断成功。

## 7. 最小实现设计

### 7.1 身份、技能与工具

身份只保存 assistantId、名称、主 threadId 和简短用户配置；不会话自动迁移、不自动写长期偏好。主会话归档或丢失时暂停自动回传，由用户显式恢复绑定；旧回传先对账。

`cxcodex-assistant-core/SKILL.md` 只规定直答/派发、澄清、读取状态、停止、转述证据和未知状态解释。`worker-brief.md` 包含本次目标、材料、允许动作、检查要求和“结果/出处/检查/未完成项”的交付提示。两者是包内受信任静态资产；不建插件系统、通用技能路由器或版本迁移引擎，派发记录必要版本/hash。

| 协调工具 | 行为 |
| --- | --- |
| assistant_dispatch_task | 校验真实用户来源、项目和权限，持久受理不可变 task，返回编号与派发状态 |
| assistant_read_tasks | 有界读取任务、真实状态、结果出处和原生待处理请求 |
| assistant_stop_task | 对助手拥有的任务记录幂等停止意图；复用现有 interrupt/队列撤出，对账实际生效状态 |

三个工具仅注册给主助手；工作线程和普通线程均无助手协调工具。worker 通过原生执行记录交付，不主动给父线程发任意消息。停止工具仅当前真实用户要求可调用；内部结果摘要回合不能产生派发或停止授权。

来源去重锚点是已鉴权、持久保存的当前 sourceUserRequestId/clientMessageId，不能用正文或原生 turnId 代替。后端解析同一助手的真实用户消息引用，包含原目标、当前澄清及期间限制；模型不能自造来源或挑旧授权。一个来源对应唯一 task；相同契约重投返回原回执，不同契约返回冲突。

主会话按独立请求串行处理，忙碌时进入同一 durable 队列；不通过 steer 把新请求或自动回传并入活动 turn。真实用户来源与内部结果来源必须贯穿队列、实际 turn 和恢复；不能靠正文或缓存的“上次用户”猜测归属。

### 7.2 仅两类新增持久记录

复用现有 Runtime SQLite，建议两张小表，不新增服务或外部数据库：

| 记录 | 必要内容 |
| --- | --- |
| assistant | 身份、主会话绑定、用户配置 |
| assistant_task | taskId、assistantId、sourceUserRequestId、sourceRefs、relatedTaskId、不可变目标/项目/权限/资产版本与 contractHash、稳定执行 requestId/clientMessageId、实际 worker thread/turn 关联、停止意图、结果快照/原文引用、冻结回传 payload、reportMessageId、reportStatus、实际主回传 turn、时间与错误 |

结果和回传意图在同一事务保存。task 只保存协调关系与结果出处，运行态从 Runtime 推导；RPC 发送阶段放在既有 Runtime 请求中，由所有启动和恢复入口共同校验。reportStatus 仅区分 pending、accepted、finished、attention；它不表示业务验收或用户已读。

一 task 一次执行且只自动回传一次，不设多 attempt 或报告批次。结果捕获、task 来源、执行请求和 reportMessageId 各有唯一约束；同一主会话只允许一个待完成的自动回传。单宿主调度仍须证明互斥，不能用“规定单实例”替代防止重复外发的机制。

### 7.3 派发与停止

先保存 task 和稳定执行身份，再复用 Runtime 可靠入口创建工作线程。Runtime 在 thread/start、turn/start 前持久记录“可能已经发送”；只有能证明尚未发出的请求才继续原发送。未知创建/启动保留待核对状态，占用执行槽位；不能按标题、目录或时间猜认线程，也不创建替代线程。

worker 的项目、sandbox、approval 和角色范围由后端按实际用户授权构造。主助手保持受限写入，原生递归/跨线程控制不能绕过统一调度；角色限制不依赖技能文字。对账与恢复必须核验实际线程权限和资产；不能仅凭 threadId 恢复执行。

停止是一个幂等意图，无修订版本竞争。已经结束时说明事实；未启动时证明请求已撤出且不会外发；已启动时发原生 interrupt，并等待权威终态。interrupt ACK 或本地 stopped 不足以释放执行槽位。

### 7.4 结果回传

```text
用户 → 主助手 → task → Runtime → worker thread/turn
                                      ↓ 真实终态/final
主助手原生摘要 ← 同一 durable 队列 ← task 结果与回传意图落盘
```

后端按精确 worker thread/turn 捕获终态、明确 final、产物/检查引用；事件只是触发器，快照/历史补偿漏事件。确定未启动的失败也保存结果；超时不能冒充确定失败。结果仅保留有界摘要与原始记录引用，不向主助手灌入完整日志。

worker 已结束但 final 暂缺时保持结果待核对，做有界补读；失败、中断或明确未产生 final 可以回传对应事实。已有回传冻结后，迟到材料不改写原正文、不触发第二次自动摘要；用户查询时可读取最新原始记录，明确它与原摘要的时间差。

结果与 pending 回传先落盘；冻结的 reportMessageId/payload 沿原身份进入现有主会话队列。主会话空闲且无待回应原生请求时才启动摘要回合，不新建后台发送器、不打断活动回合；连续用户输入可能延后摘要，任务列表仍可查询结果。不额外设计合批、公平调度或多消费者租约。

accepted 只表示回传已持久受理；finished 要求精确绑定的实际主 turn 成功结束并有明确 final。请求 completed/原生队列交接不算 finished。回传失败、无 final 或身份无法核对时进入 attention，保留结果，供用户查询或显式恢复；不自动再生成一轮。attention 不是重复发送或释放未知回合占用的依据，终态仍未知时继续对账。

摘要是普通原生对话，照常流式展示并使用现有单一会话投影。删除事务发布承诺后不再需要 prepare/publication 或未发布正文展示门槛；助手应提供出处并说明未验证项。此路径不保证摘要内容正确、目标已达成、手机通知已送达或用户已读。

### 7.5 重启恢复

| 已保存事实 | 动作 |
| --- | --- |
| task 已受理，证明 RPC 未发出 | 沿原 request/clientMessageId 继续 |
| 可能已创建/启动，实际身份不明 | 待核对并占槽；不重跑 |
| worker 仍活动或等待审批/输入 | 恢复快照和监听；原请求身份重新核验 |
| worker 已结束，结果未保存 | 从原 thread/turn 补捕获；确定启动失败也补保存 |
| 结果已保存，回传未受理 | 以原 reportMessageId 和冻结 payload 接入队列 |
| 回传 accepted 或可能已发送 | 先核对原请求和实际主 turn；只跟踪，未知不重发 |
| 主回传 turn 已结束，状态未写 | 精确绑定的实际主 turn 成功终态且有明确 final 时幂等补 finished；失败/中断或无 final 为 attention；终态仍未知则继续对账 |
| 主会话丢失或权限不兼容 | 暂停自动调度，任务与结果保留可查 |

恢复是扫描已有任务并核对原执行，不是任务重试系统。一个协调模块负责受理、调度、监听和恢复，SQLite 操作与工具适配按现有模块边界分文件；不引入单独 daemon 或通用编排框架。

## 8. 开发顺序与完成条件

1. 实际协议验证：主助手工具可调用；真实用户/内部来源与实际 turn 可关联；角色、权限和同队列独立请求生效；发送门闩覆盖所有恢复入口；宿主/Runtime 互斥有效。未证明的能力不作为已存在功能。
2. 只读闭环：身份 + 三工具 + 两类记录 + 单 worker + 原生结果捕获 + 单次回传 + 最小任务列表。用“分析项目 A 的发送流程，不修改文件”留下真实端到端记录。
3. 定向故障验收：重复派发、跨 turn 澄清、无 turn 的确定启动失败、RPC 未知、网页关闭、主助手忙碌、结果/回传断点重启、停止未证实不放行新执行。通过后再验证受授权写任务。

实现阶段按变更运行仓库既有定向检查并更新 tests.md；构建通过不能代替真实闭环。当前只完成方案调整，没有创建技能、表、工具或测试新功能；Git、部署、打包和发布仍需用户明确请求。

对外承诺限定为“一个入口、可追踪派发、持久结果、原执行对账”。如果后续确实需要同任务持续续办、业务验收结算或多实例协调，再按使用证据恢复对应设计，不预埋整套 v0.3 机制。
