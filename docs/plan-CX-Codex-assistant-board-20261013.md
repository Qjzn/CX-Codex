# CX-Codex 助手看板（Assistant Board）规划 v0.7

日期：2026-10-13。状态：**规划草案，未实现**。配套：`PRD-CX-Codex-Personal-Assistant-Lite-v0.5.md`、`CX-Codex-Assistant-P0-Protocol-Review.md`、`PRODUCT_GOAL.md`。

> v0.7 修订说明：本文档第 2、5、7 节（只读投影、零写操作）是 v0.5 版本写的；第 7.5 节（拖拽写意图）是应需求追加的 v0.6 修订，二者在"零写"这一点上自相矛盾。评审结论见第 0 节：**保留第 0 节、3、4、5（除第 5 条）、7.5、8；第 2 节与第 7 节的"只读/零写"措辞作废，以第 0 节的「最小写入面」为准。**

## 0. 评审结论（先给结论）

**值不值得做**：值得，但价值在「出问题时的排查与对账」，不在「拖拽」。拖拽是外壳，我建议先不做真拖拽。
**可不可靠**：当前版本不可直接开工——有三处硬伤（节 0.2），都必须先修。

### 0.1 五条硬伤

1. **文档自相矛盾（形式错误，必须修）**：第 7 节写着"新建表或第三协调记录=不做"，第 7.5.3 又要新增 `assistant_intent` 表。同一文件两条相反规定——这正是你们评审里最反感的"提示词当保证"。→ 二选一：复用 runtime_requests 的类型字段（推荐，零新表），或正式把新表写进 PRD 并删除第 7 节相关条目。
2. **看板不是无成本的**：执行侧数据在我这台机器的 Hermes 上（看板库、supervisor/health、cron 库、微信额度）。CX-Codex（浏览器里）要拿到这些，必须在本机跑一个只读桥接进程读文件并暴露给页面——它本身就是新的写入面和新的故障点。v0.5 用"只读投影、零写"掩盖了这件事。
3. **轮询写快照**：P2 写的"轮询快照 3–5 秒"，如果落盘缓存，就是周期性写文件（非业务状态，但算写入），与"零写"冲突；若只是内存对象则要明说。
4. **拖拽的对手方不存在**：D1 完成前，协调层没有可信入口可以消费意图。也就是说，拖拽做出来只能看、点了不生效；而 D1 才是真正难的那部分（真实用户来源绑定、精确 turn 映射、幂等受理）。先做拖拽等于先做外壳。
5. **列与权威状态的关系没定义**：四列读的是 `assistant_task` 的哪个字段？谁有权把卡放"阻塞"？存量数据只有部分状态、缺的部分显示成什么？没定义的话 UI 一定会替权威状态做判断，那才是真正危险（显示错比拖不了更糟）。

### 0.2 我的建议（不是折中，是取舍）

**第一期只做只读看板，不做拖拽**，理由：
- 只读看板解决的是真问题（卡了看不见 / 对不上账），而拖拽解决的是手感问题——你现在的痛点大概率是"它到底在干嘛"，不是"我手痒想拖一下"。
- 只读版零新表、零新依赖、零业务写路径，能独立于 D1–D4 交付并立刻有用；拖拽版必须在 D1 之后才有意义，否则做出来就是个动画。
- 拖拽的真实成本不在组件本身（dnd-kit 不贵），在**语义**：状态机、审计、幂等、部分失败、并发被拒的提示。这部分现在拿不出证据能一次做对。

**如果坚持要拖拽**：定位必须降一级——"看板视图 = 意图表达"（我第 7.5 节写的那套），且必须先补三条程序保证（谁有权拖、意图与权威状态的关系、被拒时的落地），再动手。拖拽绝不能直接改权威状态，否则就绕过了你们冻结的门闩、来源绑定和单槽争用。

### 0.3 可靠性上的真风险（比拖拽更重要）

- **分歧才是杀手**：CX-Codex 说"执行中"、Hermes 说"已完成"的时候，看板显示哪一个？这条必须先有规则（我的取向：显示双方 + 显式标注分歧，绝不自动择一），否则看板会变成第二个权威来源。
- **未知态的可视化不能降级为失败**：门闩置位无 ID、快照陈旧，渲染成红/失败就是新误判源。这条是看板的第一号风险，优先级高于拖拽。
- **"看板推着状态走"的诱惑**：一旦拖拽能改状态，就会有人用它绕过来源鉴权。要么不做，要么把意图表做成唯一入口并且协调层有权拒绝——现在两者都没有。

## 1. 一句话

在 CX-Codex 里加一个看板页：把「主助手 + 单 worker 槽 + assistant_task 记录 + 执行侧真实状态」投影成一屏，让操作者一眼看到助手系统在做什么、卡在哪、哪一步的结论还没落到权威状态上。**写入面最小化**：只写意图，不写业务状态。

## 2. 边界（替代原「只读」论证）

1. 权威状态在 Runtime（`runtime_requests` / `thread_runtime_snapshots` / `runtime_thread_leases` / `runtime_events`）与 `assistant_task`（协调事实）里；看板自身不构成第二权威源。
2. 看板不触碰派发门闩、来源绑定、单槽争用与冻结契约，因此不是自动派发的前置，可与 D1–D4 并行推进（第一期）。
3. 看板必须能表达「未知」：已外发未确认、门闩置位无 ID、快照陈旧 90s、`inProgress=false` 都不能当作停止或失败。

## 3. 数据源（含已验证项与待固化项）

### A. CX-Codex 侧（同进程库，只读）
已在源码核实（`src/server/runtimeStore.ts`）的权威表：

| 表 | 看板用途 |
| --- | --- |
| `runtime_requests` | 每次派发/回传请求、clientMessageId、每段首次发送权（外发门闩）状态 |
| `thread_runtime_snapshots` | 线程快照（inProgress / waiting_permission / 快照时间）→ 新鲜度必须显示 |
| `runtime_thread_leases` | 单槽持权、租约、所有者（跨宿主互斥的落点） |
| `runtime_events` | 事件流（用于任务时间线与追溯） |
| `runtime_metadata` | 版本/身份类元数据 |

配套（PRD §3 拟新增的两类记录）：`assistant`（身份绑定、主 thread、activeTaskId、activeReportTaskId）、`assistant_task`（来源引用、contractHash、真实 worker thread/turn、停止意图、结果出处、回传 request/payload hash/status、实际主 turn、时间与错误）。

待 P1 固化：`runtimeDatabasePath` 的实际落点（由宿主传入，源码默认值未在此环境确认）、当前运行形态是 dev 还是打包版、库文件锁与只读打开方式（`file:...?mode=ro&immutable=1`）。

## 4. 一屏四区（字段级）

**A 顶部状态条**：主助手身份与主 thread、忙碌/空闲、`activeTaskId`、`activeReportTaskId`（回传占用）、门闩置位情况、快照时间与新鲜度（>90s 标黄并注明「不可作停止判据」）。

**B 单槽卡**：持权 task、启动权来源（正常派发 / 恢复）、worker thread 与 turn、开始时间、租约与心跳、**未知占槽**标注（门闩已置位但无 ID → 显示「未知-对账中」，禁止显示失败）。

**C 任务流水**：每行一条 `assistant_task`。展示 来源 → 状态链（已受理 → 已派发 → 执行中 → 结果已存 → 回传已受理 → finished｜attention）＋停止意图＋错误＋时间。行内展开：contractHash、payload hash、clientMessageId/requestId、结果出处、实际主 turn。

**D 执行侧与对账**：Hermes 未结束任务与执行者占用、最近完成、网关与平台、cron 最近运行、微信额度；对账差异列表（红＝需人处理，黄＝待观察）。

## 5. 语义纪律（硬规则，沿用已冻结语义）

1. **未知 ≠ 失败**：门闩已置位、无 threadId 的不确定创建、晚到 ID 一律显示「未知-对账中」。
2. **不用 `inProgress=false` 判定停止**：必须显示快照年龄；陈旧/降级单独标记。
3. **accepted ≠ finished**：回传受理只显示「已受理」；finished 必须绑定实际主 turn 成功且有明确 final。
4. **单槽 = 启动权争用**：只显示持权者与等待者，不显示「计数」。
5. **最小写入面**（替代原「零写操作」）：业务状态一律不写；唯一允许的写入是 §7.5 的意图记录（或其等价物）；不派发、不停止、不重试、不改 payload/hash、不碰门闩与租约。快照缓存写在 runtime 目录之外且不被 Runtime 读取；若缓存落盘，须在评审时显式声明并纳入验收。
6. **每字段可追溯**：标注来源表/时间戳，UI 可展开看原始记录（只读）。
7. **分歧显式化**（v0.7 新增）：CX-Codex 侧与执行侧结论不一致时，显示双方并列并标注分歧，禁止 UI 自动择一。

## 6. 分三期

| 期 | 内容 | 验收 |
| --- | --- | --- |
| P1（1–2 天）**只读聚合器** | 固化数据源路径 → 生成 `snapshot.json`（schemaVersion / generatedAt / 每字段来源与新鲜度）→ 用真实数据出 HTML+Markdown 预览供字段评审。不改产品代码 | 契约字段 100% 映射；未知态标注正确；新鲜度可用；**零写操作**（SQLite 只读打开 + 无 POST） |
| P2（3–5 天）**页面接入** | 在 CX-Codex UI 加只读页面，轮询快照（3–5s），差异高亮，陈旧态显式 | 页面与快照抽样一致；断网/陈旧态显示正确；抓包证明零写请求 |

## 7. 明确不做

派发/停止按钮、任务编辑、二次回传触发、**新增业务状态表或第三协调表**（意图记录的落点见 §7.5.3 与 §0.1 第 1 条，评审时定；若确需新表，须先写进 PRD 再动）、后台轮询写入业务状态、多实例状态聚合、把看板数据当业务状态参与决策、在看板上放「已支持派发」之类暗示文案、**在第一期实现拖拽**（评审建议：第一期只读，拖拽留到协调层可信入口就绪后）。

## 7.5 拖拽流程（v0.6 修订：从只读投影改为「看板视图 = 意图表达」）

用户要的是看板流程有真实手感：把「阻塞」的卡拖到「进行中」，把「进行中」的卡拖到「关闭」。这不是只读投影能覆盖的，但也不能让拖拽直接改运行状态（那会绕过冻结的门闩、来源绑定和单槽争用）。折中方案：**拖拽写的是「意图」，不是「权威状态」；权威状态仍由 D1–D4 的程序保证推进，看板只显示意图与权威状态的关系。**

### 7.5.1 四列与语义

| 列 | 含义 | 谁能进入 |
| --- | --- | --- |
| 待处理 | 已受理、未派发 | 新建受理、从阻塞撤销 |
| 进行中 | 已派发、worker 槽占用中或有停止意图 | 派发结果、从阻塞恢复 |
| 阻塞 | 等待条件（依赖、审批、输入、租约冲突） | 执行侧报阻塞、人手动标记 |
| 关闭 | 已结清（finished / 明确终止） | 回传 finished 时自动；人手动关闭须落原因 |

「未知」不作为一列：门闩置位无 ID、快照陈旧这类不确定态，以**标记**形式挂在卡上（黄条），不另开列，避免看板自己造出第五种状态。

### 7.5.2 拖拽允许矩阵（只写意图）

| 从 → 到 | 是否允许 | 落地动作 |
| --- | --- | --- |
| 阻塞 → 进行中 | 允许 | 写意图 `resume`：由协调层下一次 tick 按来源幂等重试（不直接发 RPC） |
| 阻塞 → 待处理 | 允许 | 写意图 `requeue`：清阻塞原因，等下一次派发 |
| 进行中 → 阻塞 | 允许 | 写意图 `pause`：置停止意图 + 阻塞原因；停止结果由执行侧回执确认 |
| 进行中 → 关闭 | 需二次确认 | 写意图 `stop`：置停止意图；**必须等停止被证实**才落关闭，未证实显示「关闭中-待确认」 |
| 待处理 → 关闭 | 需二次确认 | 写意图 `cancel`，落原因，直接关闭（尚无外发，可逆性高） |
| 关闭 → 任意 | 允许（仅回收站式撤销） | 写意图 `reopen`，保留原 payload/hash，产生新的 attempt，不覆盖历史 |
| 待处理 → 进行中 | 禁用 | 派发必须走 D1 可信入口，人不能从看板凭空启动 |
| 任意 → 未知态 | 禁用 | 未知不是可拖拽的目标 |

被拒绝的拖动：卡弹回原位 + 一句明确原因（例如「派发必须走可信入口」「停止未证实，已标为关闭中」），不做无提示的静默失败。

### 7.5.3 数据与审计

- 拖拽只写一张新表 `assistant_intent`（或复用 `runtime_requests` 的类型字段，P1 评审时定）：`intentId / taskId / from / to / reason / actor / createdAt / appliedRequestId(nullable) / result`。
- 意图是**声明**，不是状态迁移；权威状态迁移仍由 D1–D4 写，写完后看板把意图标记为 `applied` 或 `rejected`。
- 拖拽是可逆的：非关闭类的意图在下一 tick 前可撤销；关闭类留下不可变审计行（谁、何时、什么原因）。
- 拖拽入口需 D1 完成后才可真正让执行侧响应；D1 之前页面可用，但意图只入队不生效，卡上显示「意图已记录，等待协调层启用」。

### 7.5.4 与只读原则的关系

看板不再完全只读，但**写权限被限制为单一意图表**：不提供派发、不直接发 turn/interrupt、不修改 payload/hash、不碰租约与门闩。因此它依然不是自动派发的前置，也不承担来源鉴权——来源可信仍由 D1 判定，看板只提交「人想让它去哪」。

### 7.5.5 验收要点（P3 追加）

- 拖动矩阵逐格验证：允许的 6 种落位有意图记录，禁止的 2 种被拒且提示原因。
- 「进行中 → 关闭」在停止未证实时的显示与后续：必须停留在「关闭中-待确认」，直到执行侧回执证实停止；不得凭本地标记关闭。
- 撤销路径：`reopen` 后历史 attempt 与 payload hash 不变。
- 审计完整性：每条意图都能追到 actor、原因、落地 request 或拒绝理由。


## 8. 与 P0/P0-B 的关系

看板不构成对 §5 门闩或 §8 程序保证的任何替代——拖拽只写意图表，真正的状态推进仍必须走 D1–D4 写路径；P0-B 通过前，页面文案必须明确「助手功能尚未启用」，拖拽意图只入队不生效，避免看板造成「已经可用」的错觉。
